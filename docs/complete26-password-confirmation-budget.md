# CR: bounded slow password confirmation

Base: `7da5b006c20d0762fe858280d557882609e3890d`. Customer problem: a successful password exchange can be followed by a valid but slow server identity check; the ordinary 10-second browser deadline rejects it prematurely. Root-observed service timings motivate this change, but are not reproduced here as hosted evidence.

Scope: only the explicit password exchange's same-user server confirmation receives a 30-second **combined fetch and response-body** budget. Ordinary/background session reads, logout and logout reconciliation retain 10 seconds. One password submission and one confirmation read; no retry, cache, API, identity, permission or backend change. Existing epoch/sequence/expected UUID checks and optional-profile isolation remain intact. A late response must not resurrect a signed-out, unmounted or superseded identity.

Validation: focused offline tests execute extracted actual provider methods and the unchanged real browser transport against a synthetic clock. A new isolated Chromium/WebKit spec exercises the rendered login with a held synthetic confirmation and browser clock; root runs it separately. No hosted calls or service-latency improvement are claimed.
